# VELOX KADENS: Image Sequence Site

אתר תדמית פיקטיבי לנעל ריצה, בנוי כ-**Image Sequence**: עשר סצנות וידאו פורקו ל-970 פריימי JPEG שמצוירים על `<canvas>` ומונעים על ידי אינטראקציה של הגולש במקום נגן וידאו.

שתי גרסאות אינטראקציה חולקות את אותם פריימים, פונטים וקופי:

| גרסה | קובץ | התנהגות |
|---|---|---|
| לחיצה | [`site/index.html`](site/index.html) | גלילה או לחיצה מנגנת סצנה שלמה פעם אחת, נעצרת על הפריים האחרון וחושפת טקסט. סצנה 10 בלופ אינסופי. |
| סקרול | [`site/scroll.html`](site/scroll.html) | מיפוי 1:1 של מיקום הגלילה לאינדקס פריים, עם האטת lerp. גלילה אחורה מריצה את הסצנה לאחור. |

`index.html` בשורש הוא דף נחיתה שמקשר לשתיהן.

## הרצה מקומית

```bash
python -m http.server 5173
```

הפונטים ו-`frames/` נטענים בנתיבים יחסיים, ולכן חייבים HTTP server. פתיחה ישירה של הקובץ מהדיסק לא תעבוד.

## מבנה

```
index.html              דף נחיתה

site/frames/1..10/      97 פריימים לכל סצנה, 1280x720 (001.jpg .. 097.jpg)

site/frames-pt/1..10/   חיתוך מרכזי 9:16 ב-405x720, לטלפונים במצב פורטרט

```

## פרמטרים לכיוונון

שני הקבצים מתחילים באובייקט `CONFIG`:

```js
scenes: 10          // מספר הסצנות
frames: 97          // פריימים בכל סצנה
fps: 24
pxPerFrame: 24      // (סקרול) מרחק גלילה לפריים. גבוה = איטי יותר
smooth: .1          // (סקרול) lerp לגלגלת/משטח מגע. ברירת המחדל של Lenis. מנורמל לזמן אמיתי
smoothTouch: 1      // (סקרול) טאץ' ללא lerp: למכשירי מגע כבר יש מומנטום מהמערכת
introPx: 220        // (סקרול) גלילה על התמונה הפותחת לפני שסצנה 1 מתחילה
holdPx: 520         // (סקרול) אזור העצירה עם הטקסט אחרי כל סצנה
```

## למה הגלילה בטאץ' לא מוחלקת

זו הבחירה החשובה ביותר בקובץ. Lenis, ספריית ה-smooth scroll הנפוצה, [מכבה החלקה במגע כברירת מחדל](https://github.com/darkroomengineering/lenis): למכשירי מגע יש מומנטום נייטיבי שמכויל לאצבע, ו-lerp נוסף מעליו גורם לפריים לפגר אחרי האצבע. אנשים מדווחים על זה כ"נתקע". לכן `smoothTouch: 1` (מעקב 1:1) והחלקה רק לגלגלת.

עוד שלוש החלטות ביצועים בלולאת הרינדור, כולן נמדדו:
- **כתיבות DOM מסוננות.** ה-tick רץ בקצב הרענון; לפני הסינון כל פריים בטלה עשה ~40 כתיבות class/style. עכשיו 0.
- **ציור רק כשהפריים השתנה.** `drawImage` לא רץ אם התמונה זהה לקודמת.
- **resize מסונן.** דפדפני מובייל יורים resize בכל הצגה/הסתרה של שורת הכתובת. בונים את הקנבס מחדש רק על שינוי רוחב או קפיצת גובה של 160px+ (סיבוב).

## איך גרסת הסקרול טוענת

הגלילה נתקעה בעבר כשגולש הגיע לסצנה שהקבצים שלה עוד לא ירדו. שלושה מנגנונים פותרים את זה:

1. **שתי רזולוציות.** סט הפרוקסי (14MB לכל הטיימליין) נטען לפני ההיי-רז (68MB), כך שלכל מיקום גלילה יש פריים תוך שניות. ההיי-רז מחליף אותו כשהוא מגיע.
2. **חימום פענוח בחלון נע.** הפריימים נשמרים כאובייקטי `<img>` (בייטים דחוסים שהדפדפן רשאי לפנות), ורק החלון סביב הפריים הנוכחי מפוענח מראש עם `decode()`.

   > אזהרה למי שנוגע בקוד: **אסור** להחזיק פריימים כ-`ImageBitmap`. 970 פריימים ב-1280x720 RGBA הם 3.4GB של פיקסלים שהדפדפן לא יכול לשחרר, וזה מפיל טאבים בנייד. זה קרה בפועל.
3. **תור לפי עדיפות.** סדר הטעינה מחושב מחדש בכל החלפת סצנה: פרוקסי של הסצנה הנוכחית, פרוקסי של השאר, ואז היי-רז מהסצנה הנוכחית קדימה ואחורה.

סולם הנפילה בציור: היי-רז מדויק, אחרת פרוקסי מדויק, אחרת הפריים הקרוב ביותר מכל רזולוציה. ה-pill "טוען פריימים" מופיע רק כשאין פריים מדויק בכלל.

**מכשירים חלשים.** מסך צר מ-900px או `deviceMemory` של 4GB ומטה נשארים על סט הפרוקסי בלבד: 640x360 עובר את הרזולוציה של מסך טלפון ממילא, וזה מוריד את ההורדה מ-82MB ל-14MB ואת תקרת הזיכרון בהתאם.

**טלפונים בפורטרט.** פריים 16:9 שמותאם ל-cover על מסך 9:19.5 מציג רק ~26% מרוחבו, ומגדיל את הפרוקסי פי 2.3. לכן טלפון בפורטרט (יחס גובה/רוחב מעל 1.4) מקבל את `frames-pt/`: חיתוך מרכזי 9:16 בגובה 720 מלא. אותו משקל קבצים, פי 2 חדות, ו-82% מהפריים נראה. הבחירה נעשית פעם אחת ב-boot; סיבוב המכשיר טוען מחדש כדי לבחור את הסט המתאים.

**רספונסיביות.** כל ה-CSS למובייל יושב בשני בלוקים של media query (`max-width:640px` ו-`max-height:520px`). דסקטופ ב-1280x720 לא נוגע באף אחד מהם; זה נבדק בהשוואת 464 שדות של computed style לפני ואחרי, אפס הבדלים.

## בנייה מחדש של הפריימים

הסרטונים המקוריים אינם בריפו. החזירו `1.mp4` עד `10.mp4` ואת התמונה הפותחת לשורש והריצו:

```bash
bash build-frames.sh
```

## הערה

הצילומים בסרטונים הם של **On Running**, כולל לוגו וכיתוב על הנעל. זהו תרגיל עיצוב ולא חומר שיווקי אמיתי של VELOX. הנתונים הטכניים באתר (EnergyRod, Lightstrike Pro, אחוזי החזר אנרגיה) הומצאו לצורך התרגיל.
